# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a Unity 3D top-down tactics game inspired by Valorant. It is built with the **Universal Render Pipeline (URP)** and uses the **New Input System**. The project namespace is `Tactics`.

## Assembly Definitions

| File | Assembly | Purpose |
|---|---|---|
| `Assets/Scripts/Tactics.asmdef` | `Tactics` | All runtime game code |
| `Assets/Tests/EditMode/Tactics.Tests.EditMode.asmdef` | `Tactics.Tests.EditMode` | NUnit edit-mode tests |
| `Assets/Editor/Tactics.Editor.asmdef` | `Tactics.Editor` | Editor-only utilities |

## Running Tests

Tests run through Unity's Test Runner (Window → General → Test Runner). The edit-mode tests in `Assets/Tests/EditMode/` use NUnit and do not require entering Play Mode — they test pure-logic classes like `VisionEvaluator` directly.

There are no CLI build or lint commands; all compilation happens inside the Unity Editor.

## Architecture

### Game Loop (`GameManager`)
`Assets/Scripts/Core/GameManager.cs` is a singleton that drives the match lifecycle via a coroutine: **BuyPhase → RoundActive → RoundEnd**, then loops. It fires `OnStateChanged` and `OnTimerUpdated` events that other systems subscribe to. `EconomyManager` is informed at round end.

### Player
- `PlayerController` (`Tactics.Player`) — movement (run/walk/crouch via `CharacterController`), mouse-aim rotation, and the camera aim lock (below). Exposes `VisionOrigin`, `LookTarget`, and `AimGroundPoint` for downstream systems.
- `TopDownCamera` (`Tactics.Camera`) — orthographic-style top-down camera locked at 90° X rotation. Follows player + mouse midpoint. `QuickAlign` coroutine snaps to a given Y-rotation (currently unused by gameplay — kept for a future re-center binding).
- **The camera yaw follows the aim, with a deadzone.** By default `PlayerController.HandleAimLock` feeds the player's facing to `TopDownCamera.FollowAimYawWithDeadzone` every frame: `CameraFollowMath.DeadzonedYaw` holds the yaw target *untouched* (bit-identical, so a jittering aim can never creep the view) while the aim sits within `aimLockYawDeadzoneDegrees` (25°), and past the edge drags it by only the excess, leaving the aim exactly ON the band edge so the band re-centers as the turn continues. Holding **Caps Lock** (the `CenterCamera` action) is the escape hatch, and does nothing but stop that call: the yaw freezes wherever it had reached — the classic fixed-yaw view — while the character keeps facing the mouse as always. Release resumes the follow and the existing `SmoothDampAngle` drags the view back onto the aim in ~0.2 s. Nothing snaps and the cursor is never warped, so the crosshair stays exactly where the player put it. This is the inverse of the original binding, where the camera was fixed until Caps Lock was held and then tracked the aim 1:1. The follow is skipped while a menu is open, next to the aim itself being frozen on its last offset there.

### Vision System
The most complex subsystem. Two parallel layers cooperate:

**CPU layer (entity visibility)**
- `VisionEvaluator` — stateless static methods: cone tests, LOS raycasts, capsule sample-point collection. No Unity scene state; fully testable.
- `VisionConfig` — plain value struct passed to all evaluator calls.
- `EntityVisibilityDriver` — iterates every registered `VisibleEntity` each `LateUpdate` and calls `VisionController.IsEnemyVisibleAt`; toggles their renderers.
- `VisibleEntity` — self-registers in a static list; holds `FeetPosition` and optional capsule overrides.

**GPU layer (fog of war)**
- `VisionController` — owns a hidden perspective "eye camera" placed at the player's head. Each frame it renders depth into `_VisionEyeDepth` (R32F). Sets all `VisionShaderGlobals` for shader consumption. Temporarily disables the player's own renderers during the eye-camera pass to avoid self-occlusion.
- `VisionFogRendererFeature` (URP `ScriptableRendererFeature`) — enqueues `VisionEyeDepthCapturePass` on the eye camera and `VisionFogCompositePass` on all other game cameras.
- `VisionEyeDepthCapturePass` — copies the eye camera's depth buffer into the persistent R32F texture.
- `VisionFogCompositePass` — fullscreen blit pass.
- `VisionFogComposite.shader` — reconstructs world-space positions from the scene depth buffer and for each pixel tests four sample heights (head/chest/knees/feet) against the eye depth map. Pixels not visible are darkened by `_FogStrength`.

**Layer indices** (`VisionLayerMasks`): Wall=6, Ground=7, Dynamic=9; `WallOnly` is the mask both bullet- and melee-blocking queries use. Map geometry never carries these layers on its visual objects: the importer splits every map object's faces by normal into a `GroundCollider` child (Ground, within 45° of up) and a `WallCollider` child (Wall, everything else), which is what lets players aim onto prop tops and ramps without the geometry being hand-cut — see *Map import*.

### Combat (server-authoritative)
- `Health` — `NetworkBehaviour`; server-only mutators (`TakeDamage`, `AddShield`, `Heal`, `ServerRevive`) with shield-first absorption, replicated via `NetworkVariable`s; `OnHealthChanged`/`OnShieldChanged`/`OnDeath` fire on every peer from the replicated values.
- `WeaponController` — owner computes the aim point (world position under the mouse) and sends `ShootServerRpc(aimPoint, weaponId)`; the server re-validates fire cadence, resolves the hit against its own world (wall penetration, see below; proximity damage rings on the XZ plane: head <0.5m, body <0.75m, leg <1m), and applies damage. `weaponId` indexes the `weaponRegistry` array serialized on the Player prefab so the server reads stats from its own `WeaponData` copy. Ammo/inventory are still client-trusted until the buy/economy systems are networked.
- **Wall-bang (penetration)**: two independent axes, matching measured Valorant behaviour. The *surface* decides how far a bullet may travel (`SurfaceData.maxTravelMeters`, a plain horizontal thickness in metres — Wood 1.0, Stone 0.7, Concrete 0.6, Metal 0.45, unlabelled 0.8; read per FACE from the `SurfaceMap` on the crossed `WallCollider` child via `RaycastHit.triangleIndex`; entry and exit faces can differ, and the tougher of the two governs); the *weapon's* `PenetrationLevel` (Low/Medium/High on `WeaponData.wallPenetration`) decides the damage curve played out over that distance. A weapon's level therefore never changes *which* walls it can pierce — an Operator and a Classic get through the same geometry, the Classic just arrives with far less. Damage never reaches zero: every level bottoms out on a floor (30% medium/high, 25% low), which is what reproduces the measured minimums (Vandal 160→48, Sheriff 159→47, Spectre 78→19, Bucky 40→10). The curve is analytic, not banded — `mult = floor + (start − floor)·(1 − u)^k` over `u = clamp01((t − head)/(1 − head − tail))`, with a flat `head` at the start (only High keeps full damage through real wall) and a flat `tail` at the end (Low sits on its floor early); all five parameters per level live in `WallPenetration`. Travel distance follows Valorant's "one solid wall" rule: **first entry → last exit**, so air between two pierced objects counts as wall, but a single wall plus a long gap to a distant target costs only its own thickness. Mixed materials are governed by the most restrictive one. Deliberate divergences from the source testing: the Operator's outlier 0.41 floor is treated as a thin-wall artifact (it floors at 0.30 like every other High weapon), and the rare ~2-in-100 "tail" to ~10% at the extreme tip is not reproduced.
- **Shot origin is the eye, and the player's origin is the WAIST.** The CharacterController is centred on the transform (centre 0, height 2), so the origin sits a metre above the soles while every body height in the project — `eyeHeight` 1.5 standing, 1.0 crouched — is measured from the feet. `ShootServerRpc` therefore raises `startPoint` by `EyeHeightFor(crouched) − PlayerMovementNetwork.FeetToOrigin`, the arithmetic living in `PlayerGeometry` (standing that is +0.5, exactly the VisionOrigin's local offset on the Player prefab). Using the eye height straight off the origin puts the shot a metre above the eyes — it sails over low cover instead of through it, which is what `PlayerGeometryTests` pins down. Penetration is then measured on a **horizontal** segment at that height: the damage model is XZ-planar throughout (`FindClosestTarget` and the hit rings ignore y), so measuring the wall in that same plane is what lets a surface's budget be read as a plain thickness. Spread is unaffected — `ApplyOffsetToAimPoint` zeroes y. Tracers and blocked-shot decals start/land at eye height.
- **Alt-fire (ADS)**: weapons with `WeaponData.altFireType == AimDownSight` aim via right click — `adsMode` Hold (Vandal: aim while held) or Toggle (Operator: each press cycles no-zoom → level 1 → ... → no-zoom through `adsZoomLevels`, e.g. [2.5, 5]). Aiming narrows the vision cone by the level's tan-space multiplier (pure logic in `AdsZoomLogic`, smoothed in `VisionController`), slows movement (`adsMoveSpeedMultiplier`, per-weapon), scales fire rate (`adsFireRateMultiplier`), swaps spread to the alt-fire column (`altFirstShotSpread*`/`altMaxSpread*`; for an ADS alt-fire only first/max are taken, growth and movement penalties stay shared with hip-fire), and biases the camera toward the crosshair — `TopDownCamera` scales its look weight from `lookWeight` toward `adsMaxLookWeight` by the tan-space zoom fraction `1 − 1/zoom` (pure math in `CameraFollowMath`), so deeper zoom (Operator level 2) pushes the player model further toward the screen edge. The camera bias never moves the *aim*: `TopDownCamera` keeps a "shadow" position (where the camera would be with no bias — bit-exact copy of the real camera while not aiming, independent sim only while the weight is diverged) and each frame warps the OS cursor so the world point under it moves only by the shadow's motion (`CompensatedAimPoint`, per-frame delta re-derived from absolute positions — never a standing offset, which runs away). Warping is skipped while a menu owns the cursor, unfocused, during `QuickAlign` (CenterCamera does its own warp), and clamps to screen bounds; `CrosshairController` runs at execution order 160 (camera 150) and prefers `WarpedCursorScreenPosThisFrame` because `Mouse.current` only reflects a warp at the next input update. ADS state flows like crouch: `PlayerController.IsAiming` (= zoom level > 0) → `PlayerInputTick.Ads` → `PlayerStateSnapshot.IsAds` → server reads `AuthoritativeIsAds`. Toggle zoom resets on weapon switch and reload start. Spread movement penalties are classified from the player's *chosen inputs* (Walk/Crouch flags in the snapshot), never from measured speed — speed modifiers like ADS must not shift the spread band.
- **Shotguns (pellets + damage falloff)**: `WeaponData.pelletCount` > 1 (Judge: 12) fires that many pellets per trigger pull from one `ShootServerRpc` — each pellet rolls its own disc offset from consecutive shot numbers (`serverShotNumber` advances by pelletCount per pull; spray index and recoil once per pull; pure logic in `SpreadCalculator.ComputePelletOffsetsDegrees`). Per-pellet base damage comes from `WeaponData.damageRanges` (distance bands with explicit head/body/leg values since ratios differ per band; looked up by XZ shooter→target distance in `DamageFalloff.GetZoneDamage`; past the last band it keeps applying; empty array = legacy `headDamage × hit-level multipliers`). Pellet damage is summed per target as floats and truncated once — a single `TakeDamage`/`HitConfirmOwnerRpc` per target reporting the best zone hit. All impact FX for a pull ride one batched `ShotImpactsClientRpc` (`PelletImpact[]`); multi-pellet decals fade after `HitFxSpawner.PelletDecalLifetime` (4 s) instead of the prefab's 10 s. `WeaponData.spreadDistanceExponent` controls how the pattern's world radius grows with aim distance (`tan(spread°) · 10^(1-exp) · d^exp`, degrees calibrated at 10 m): 1 = true angular cone (default, all rifles + what recoil assumes), Judge = 0.5 (√d) because against the fixed XZ hit rings a pure cone's hit count decays ~1/d² while measured Valorant damage decays ~1/d (tall first-person silhouette) — √d growth reproduces the measured curve (≈122 avg at 10 m, ≈25 at 20 m, ≈10 at 50 m with 8° base spread).
- **Alt-fire (shotgun burst)**: `WeaponData.altFireType == Shotgun` (Classic) makes right click a discrete 3-pellet burst rather than a stance — one burst per press (`WasPressedThisFrame`, unlike primary fire and the Judge, which repeat while held), `altPelletCount` rounds per pull at the absolute `altFireRate` (2.22/s). It owns the whole alt column: `altFirstShotSpread*`/`altMaxSpread*`, `altSpreadPerShotDegrees`, `altMovePenalty*` and `altSpreadDistanceExponent` (Classic 0.5 while its primary stays a true cone at 1). A burst off a near-empty magazine fires the rounds it has, one pellet each. Because a burst is an action and not a stance, it can't ride the tick-quantized `PlayerStateSnapshot` the way ADS does: `ShootServerRpc(aimPoint, weaponId, altShot, pelletCount)` carries the mode on the shot itself, and the server derives spread column, growth, penalties, exponent and cadence from `altShot` out of its own registry copy (`FireModeStats`), clamping `pelletCount` to the weapon's own max — so a lie can only pick a mode or reduce pellets, never mix the good halves of both. **Both fire modes share one fire timer**, gated on `max(previous shot's interval, this shot's interval)` (`FireModeStats.RequiredGapSeconds`), so a slow burst locks the gun for its full 0.45 s and interleaving can't beat the better single mode; per-mode timers would run both cadences at once. Client and server must compute this identically or the server silently swallows shots, which is why the arithmetic lives in one pure static. **Spray decay grace runs from when the gun is ready again**, not from the shot: `SpreadCalculator.DecaySprayIndex` only recovers after `RequiredGapSeconds + sprayDecayDelay`, so firing at any weapon's max cadence (including right-click bursts) always stacks toward max spread, and `sprayDecayDelay` is purely jitter tolerance plus a pause. Measuring the grace from the shot let any weapon slower than the delay (Vandal 5.4/s = 0.185 s vs 0.15 s, Judge, Classic bursts) bleed recovery into every gap, so spread barely grew.
- **Per-weapon movement speed**: `PlayerInputTick.WeaponId` carries the held weapon's registry index each tick; `Simulate()` resolves it against the server's own `weaponRegistry` copy for `runSpeedPercent` (Operator 0.95 → 5.13 m/s) and `adsMoveSpeedMultiplier` — clients pick which weapon applies but never its values.
- **Equip delay**: `WeaponInventory.IsEquipping` blocks firing, reload-start, and toggle-zoom cycling for `equipSpeed` seconds after the active weapon changes (switch, buy-into-hands, spike fallback; client-trusted like ammo).
- **Melee (Knife)**: `WeaponType.Melee` is the discriminator (not `AltFireType`, since both of its modes are swings) — `FireModeStats.IsMelee`/`IsMeleeAlt`. A swing leaves the bullet path entirely: no aim point, spread, pellets, falloff, or wall-penetration budget. The owner sends `MeleeSwingServerRpc(weaponId, altShot)` — no aim point, because the server already owns the attacker's authoritative position *and* facing — and the server rejects it unless its own registry copy agrees the weapon is melee. `ResolveMeleeServer` sweeps `HitboxHistory.All` for the nearest target inside a box straight ahead (`MeleeCombat.TryGetForwardDistance`: forward component within `meleeRange` 2 m, lateral within `HitZoneRadii.Leg` — a box, not a capsule, so reach never exceeds the stated range), rejects any target with a Wall between (a knife has no thickness budget), and picks damage by which hemisphere the attacker stands in relative to the target's facing (`MeleeCombat.IsBackHit`, rear hemisphere = behind the shoulder plane): Knife 50 front / 100 back primary, 75/150 alt, all four serialized on `WeaponData`. Primary repeats while held (1.6/s); alt is one swing per press at the absolute `altFireRate` (1.1/s) and shares the same `RequiredGapSeconds` timer as every other weapon, so knife↔gun interleaving can't beat either cadence. A swing zeroes `serverSprayIndex` like a weapon switch, raises no `EmitShootSound` (it isn't a gunshot), and spawns no FX — the only FX vocabulary is a bullet tracer plus decal, and a tracer over a 2 m swing reads wrong. The airborne ×0.5 penalty is a spread-era jump-peek rule and deliberately does not apply.
- **Lag compensation**: `HitboxHistory` (on Player and TargetDummy prefabs) records each entity's authoritative position **and yaw** per network tick, server-side only, in a static `All` registry. Yaw is what makes lag-compensated backstabs correct: `UpdateRemoteView` drives a remote player's `transform.rotation` from the interpolation-delayed view buffer *even on the server*, so front/back must be judged from `GetYRotationAt` (fed by the new `PlayerMovementNetwork.AuthoritativeYRotation`), never `transform.forward`. `WeaponController.ShootServerRpc` rewinds hit resolution by the shooter's transport RTT + remote-view interpolation delay (server-measured — clients never send timestamps), capped at 1 s. The damage model is positional (XZ rings), so no physics-scene rewind is needed. Histories are wiped on `ServerTeleport` so rewound shots can't hit vacated respawn corpses.
- Player death → `PlayerMovementNetwork.ServerHandleDeath` teleports to spawn and revives one frame later (so spike drop sees the corpse position). Target dummies use `AutoRevive` instead.

### Netcode
- `PlayerMovementNetwork` — server-authoritative movement with owner prediction/reconciliation, remote-view snapshot interpolation (`interpolationDelayTicks` behind newest), and `ServerTeleport` (bumps `TeleportCount` in the snapshot so owners clear prediction and views cut instead of gliding). **All movement must go through `Simulate()`** or reconciliation reverts it; `ServerTeleport` is the one sanctioned exception.
- `NetworkSpawnMarker` — scene marker that server-spawns a registered network prefab at its own transform on session start (used for the spike pickup and target dummies; in-scene-placed NetworkObjects are avoided because despawn-destroying them is discouraged by NGO).
- Spike carry state exists twice: the owner's local `HasSpike` (HUD/plant checks) and the server instance's `HasSpike` (authoritative — granted in `SpikePickup.TryGrant`, cleared via `ServerClearSpike` on plant/death).

### Economy (`EconomyManager`)
Valorant-style cred system: round-win (3000), loss-streak bonuses (1900/2400/2900), kill reward (200), plant reward (300). Halftime resets to 800. Fires `OnCredsChanged`.

### Objectives
- `Spike` / `SpikeController` — plant (4 s hold) and defuse (7 s hold, within 3 m of the planted spike) interactions, both gated on `GameState.RoundActive`. `SpikeSite` is gone: the site is the floor itself (below).
- **A plant site is painted floor, not a volume.** Faces carrying a Blender material whose `SurfaceData` has `isPlantSite` are the site; there is no trigger object at all. `PlantSiteQuery.IsOnPlantSite` casts a short ray down from 0.5 m above the feet (`PlayerMovementNetwork.FeetPosition` — NOT `transform.position`, which is the waist) (1 m long, past the 0.3 m step offset, `GroundOnly`, triggers ignored) and reads the struck face's surface off its `SurfaceMap`. `SpikeController` gates planting on that instead of `OnTriggerEnter`; the spike's own proximity trigger is unchanged. This replaced a convex trigger volume, which could never match a jagged site: Unity forbids non-convex triggers, so stairs or a notched corner needed several volumes or one that bulged past the visible marking. Painted floor is exactly as jagged as it looks, and jumping over a site plants nothing because the probe finds no floor.
- **A timed interaction owns the player.** While planting or defusing, `SpikeController` pushes `PlayerController.SetInteractionLock(true)` every frame, and `SampleInput` then zeroes move/walk/jump **at the source** — not in the movement sim — so the input the server replays is the same standstill the owner predicted; zeroing it later would leave the two disagreeing and reconciliation would fight the lock every tick. Stance (crouch, ADS) is left alone since it moves nobody. `WeaponController` refuses to fire or start a reload while locked (one early-out beside the equip-delay guard; `TryShoot` checks it too, covering primary, alt-fire and melee, since swings route through `Shoot()`), and `WeaponInventory.Update` refuses slot switches — the spike slot included — beside its existing reload guard. That guard sits at the input, not inside `SwitchTo`, so scripted equips (buy menu, spike fallback) still work. A reload already in flight is left to finish; only starting one is blocked. Abilities should check `IsActionBlocked` (which includes the interaction lock) once they exist. The lock is pushed per frame and released in `OnDisable`, so no interruption can leave a player frozen. Progress shows on the HUD's shared `actionBar` (the one the reload and weapon draw use) as "Planting..."/"Defusing...", taking priority over a reload, which it can legitimately overlap. Any interruption — releasing Interact, stepping off the site, leaving defuse range, the round ending — resets the timer rather than freezing it, so the bar never stalls half-full and a plant cannot resume where it left off.

### Sound
`SoundEmitter` tracks last move/shoot emit timestamps and exposes `IsCurrentlySounding` for the `SoundVisualizer` to draw radius circles. No audio clips — it's a pure gameplay-signal system.

### UI (UI Toolkit)
All screen UI is UI Toolkit, no uGUI: scene objects `HUD` (`HUDController` — ammo + weapon slots), `BuyMenuUI` (`BuyMenuController`) and `SettingsMenuUI` (`SettingsMenuController`, sorting order 10 so it draws above the rest) each hold a `UIDocument` sharing `Assets/Scripts/UI/PanelSettings.asset` (ScreenSpaceOverlay, ScaleWithScreenSize 1200×800). UI controllers find the local player lazily each `Update` via `NetworkManager.Singleton.LocalClient.PlayerObject` (the player spawns after the HUD), and must call their refresh once right after subscribing to inventory events (the default equip fires before subscribers exist).

**Crosshair** — `CrosshairController` (on the HUD object) hides the OS cursor and draws a Painter2D crosshair at the mouse: a "+" normally, and, whenever the *current* trigger pull would throw more than one pellet (a shotgun always, the Classic while right click is held — `WeaponController.CurrentPelletCount`), a circle. Both shapes read one radius, the true spread footprint at the aim point — `SpreadCalculator.ComputeSpreadWorldRadiusMeters(xzDistance, spreadDeg)` (the same `d·tan θ` projection shots use) projected to panel pixels via two `CameraTransformWorldToPanel` points. The circle *is* that footprint; the "+" arms start at `max(plusGap, footprint)` and keep their length, so whenever the "+" has grown its inner edge is exactly where the shot can land. The indicator is deliberately honest rather than readable: it is world-sized (it grows as the cursor moves farther out, directly comparable to the hit rings), unsmoothed (the server uses the instantaneous value — easing would lie exactly when counter-strafing), and excludes recoil (a deterministic drift, not uncertainty). A consequence worth knowing: movement error dominates it, and a rifle spray barely blooms it — a Vandal's spray inaccuracy is mostly recoil climb. Its inputs are owner-local and zero-latency: `WeaponController.CurrentSpreadDegrees` (an owner-side spray-index mirror advanced/decayed/reset with the same pure `SpreadCalculator` calls and on the same events as `serverSprayIndex` — cosmetic only, the server never reads it), `WeaponController.TryGetAimPoint` (the same raycast `Shoot()` sends, so crosshair and shot can't disagree), and `PlayerMovementNetwork.PredictedGrounded`/`PredictedHorizontalSpeed` (owner prediction state, not the RTT-lagged snapshot). The look comes from the player's `CrosshairSettings` (`SettingsService.Current.crosshair`, re-read every frame), including two display toggles: `showFiringError` (spray growth) and `showMovementError` (the movement penalty). Hiding one feeds the crosshair `SpreadCalculator.ComputeDisplayedSpreadDegrees`, which reads the spray as settled / the player as stationary — the stance column (crouch, alt-fire) is neither and always applies, and shots never use this. With both hidden the "+" is constant-size (`PlusShowsSpread`), while the shotgun circle still draws the first-shot footprint — which still grows with aim distance, because that is how big the pattern is there. The crosshair hides and hands back the OS cursor whenever `MenuState.IsOpen`.

**Menus and input** — `MenuState` (`Tactics.Core`) holds the one open `IGameMenu`; menus never stack (`TryOpen` refuses while another is open), so closing one can't un-hide the crosshair from under another. `SettingsMenuController` owns the `Menu` action (Esc): with a menu open it calls that menu's `Cancel()` (buy menu closes; settings closes its confirm dialog first, then itself), otherwise it opens settings. While any menu is open the mouse is not aim: `PlayerController.IsActionBlocked` (= interaction lock **or** menu open) gates firing, reload start and slot switches beside the old interaction-lock checks, the player and camera hold their last aim *offset* (so walking with the shop open doesn't swing the view), zoom-wheel, CenterCamera and cursor warps are skipped, a held ADS drops, and holding Interact cancels. `IsMovementLocked` (= interaction lock **or** `MenuState.FreezesPlayer`) zeroes locomotion at the source exactly like planting; the Esc menu freezes, the buy menu doesn't (walking while shopping is normal). The buy menu closes itself when the buy phase ends unless Always Buy is on.

**Settings** (`Assets/Scripts/Settings/`) — `GameSettings` (video, graphics, crosshair) is saved as JSON at `Application.persistentDataPath/settings.json` by `SettingsService`, which loads and applies it `BeforeSceneLoad`; `FromJson` sanitizes everything (bad file → defaults, values clamped). Edits apply instantly through `SettingsService.NotifyChanged()` and are saved when the menu closes. Window mode/resolution are the exception: they wait for Apply and revert unless confirmed within 15 s (and `Screen.SetResolution` is skipped in the Editor — test those in a build). `SettingsApplier` never touches the project's URP asset: it clones it once and installs the clone as `QualitySettings.renderPipeline`, because asset properties set in Play Mode are written to disk; `Application.quitting` restores the original asset, VSync and frame cap in the Editor. Graphics = preset (Low/Medium/High, relabelled Custom when an option diverges) + render scale, MSAA, shadows (Off is shadow distance 0). **Nothing graphical may change what a player can see of enemies**: `VisionController` forces the pipeline render scale to 1 while the eye camera renders, so a lowered render scale can't coarsen the fog depth map.

**Cheats** — match state, not settings: `MatchRules` (`Tactics.Core`, a `NetworkBehaviour` on the `MatchRules` prefab, spawned by the `MatchRulesSpawn` `NetworkSpawnMarker`) replicates server-written `InfiniteAmmo`, `AlwaysBuy` (shop in any phase) and `InfiniteCredits` (free purchases). Only the host can change them (`CanEditCheats`); clients see the tab read-only. Everything hangs off `allowCheats` on the prefab — the switch the future lobby will set — which defaults to **on** while testing; with it off every cheat reads false and the Cheats tab is hidden. Consumers read the static properties (`WeaponController.ConsumesAmmo`, `BuyMenuController`); since ammo and credits are still client-trusted, each peer applies them to its own copy, and future server-side checks should read the same properties. Only the Test scene has `SettingsMenuUI` and `MatchRulesSpawn`.

## Key Conventions

- Singletons use `Instance` with `Awake` guard (`if (Instance == null) Instance = this; else Destroy(gameObject)`).
- `VisionController.Active` is a static reference to the currently-active controller; the renderer feature accesses it this way.
- Shader property IDs are cached in `VisionShaderGlobals` to avoid per-frame string lookups.
- `[DefaultExecutionOrder(100)]` on `VisionController` and `[DefaultExecutionOrder(101)]` on `EntityVisibilityDriver` ensure vision data is ready before entity visibility is evaluated.
- The eye camera is created at runtime (`HideFlags.DontSave`) and parented to the player; it must not appear in saved scenes.

### Map import (Blender → Unity)
The map is authored in Blender and exported whole into **`Assets/Models/Maps/`**; `Assets/Editor/MapImportPostprocessor.cs` (an `AssetPostprocessor`) turns every model under that folder into playable geometry on import, so dropping in the FBX is the whole workflow. Models anywhere else (e.g. `Spike.fbx`) are never touched. The folder gate — rather than a name prefix or an asset label — keeps names free and survives deleting and re-adding the FBX. `OnPreprocessModel` forces the importer's own *Generate Colliders* off.

**Object names mean nothing. The Blender material on a face decides everything about it.** Each material name is matched (case-insensitively, ignoring Blender's `.001` and Unity's ` (Instance)`) against the `SurfaceData` assets in `Assets/Data/Surfaces/`, whose asset name *is* the key. A `SurfaceData` carries only **behaviour** — `maxTravelMeters` for wall-bang and `isPlantSite` — never the look. Note the Ground/Wall *layer* split is geometric and has nothing to do with the Ground/Wall *surfaces*: an up-facing face lands on the Ground layer whatever material it carries. Current set: `Wood`, `Stone`, `Metal`, `Concrete`, `Dirt`, `PlantArea` — one per Blender material, nothing more.

**The look stays Blender's, with no fallback.** The importer never assigns a material: every face keeps the one the FBX exported, so a look is authored once and Unity holds no second copy to keep in sync. The only time `sharedMaterials` is written at all is when the mesh had to be rebuilt, and then it is the same slot materials re-ordered to match the new submeshes. A face with no Blender material simply keeps Unity's default — nothing papers over it. (Lotus's FBX has no materials, so it renders default until re-exported; that is expected, not a bug to be patched around.) Pointing a `SurfaceData` at a material *inside* an FBX is the one thing to avoid: it is a sub-asset of the file being imported, so the import would depend on an asset that depends on it, and the link dies whenever the FBX's GUID changes.

**One Blender object stays one object**, and its ground/wall split — which the game consumes through layers (aim raycasts see only Ground, penetration and melee only Wall) — is computed from face normals by `SurfaceClassifier`:

```
Visual object       MeshRenderer + materials, no collider, Default layer
├─ GroundCollider   faces within 45° of up (walkable ramps included)   Ground (7) + SurfaceMap
└─ WallCollider     everything else, ceilings and undersides included  Wall (6)   + SurfaceMap
```

- **Surfaces are per face, not per object.** Unity imports one submesh per Blender material slot, so a concrete building with a dirt floor on top is one mesh with two slots. `MapSurfaceSplitter` (pure static, tested) tags every collider triangle with its surface, and `SurfaceMap` stores that as a palette plus one byte per triangle — read back at runtime through `RaycastHit.triangleIndex`, which Unity keeps aligned with the collider mesh's triangle order. A single-surface collider stores no per-triangle array at all.
- **An unknown material is not an error.** Its faces are still split onto the right layers by their normals; they simply get no surface, so they fall to `WallPenetration.DefaultMaxTravelMeters` and can never be a plant site. The importer logs the unmatched names once per import. There are deliberately no `Ground`/`Wall` fallback surfaces: geometry decides the LAYER, the Blender material decides the SURFACE, and the two are independent.
- **The render mesh is only rebuilt when it must be** — when an unpainted submesh splits into floor and wall, or when a slot is empty. Painted slots stay one render group each so every slot keeps its own Blender material. The rebuild copies the imported mesh (keeping normals, UVs, tangents) and only regroups index buffers. Slivers are dropped from colliders but never from the render mesh.
- 45° is deliberately the Player `CharacterController` slope limit: aimable ground means "somewhere you could stand".
- Face normals come from triangle positions, never vertex normals (smooth-shaded exports average normals across a box's edges). They are judged in root space because Blender's FBX axis conversion leaves arbitrary rotations and non-uniform unit scales on objects; a mirrored transform flips the winding back.
- Slivers — height under 1e-5 of the longest edge — are dropped from colliders. The test is scale-invariant on purpose, since mesh-space units are arbitrary. Blender's n-gon triangulation leaves zero-area T-junction triangles whose normals are noise, and a collider half made only of them fails PhysX cooking ("cleaning the mesh failed").
- Generated meshes must be registered with `context.AddObjectToAsset`, or they vanish on reload. **Bump `GetVersion()` whenever the pass's output changes**: Unity then reimports the maps by itself; without it, it keeps stale cached results and flags the next manual reimport as an "inconsistent result".

**Modelling rules that follow from the systems, not from the importer:**
- **Anything with players on both sides must be a closed solid.** Unity's mesh raycasts are one-sided (`m_QueriesHitBackfaces: 0`), so a bullet entering a one-sided wall finds no exit and stops dead, while from behind that same face is invisible — the shot passes at full damage and vision looks straight through. Map boundaries facing the void are fine as open shells; that is exactly the "stops at the boundary" behaviour wanted there.
- **Plant-site faces must point up**, or the floor probe (like every ground raycast) cannot hit them.

Scene instances of a map must carry **no** layer, material, collider or component overrides: the importer owns all of it. (Lotus still uses the old name-split export with `Trigger_` volumes and no Blender materials; until it is re-exported with materials it imports with automatic Ground/Wall looks, its trigger prisms become ordinary solids, and planting there does not work.)
