# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a Unity 3D top-down tactics game inspired by Valorant. It is built with the **Universal Render Pipeline (URP)** and uses the **New Input System**. The project namespace is `Tactics`.

## Assembly Definitions

| File | Assembly | Purpose |
|---|---|---|
| `Assets/Scripts/Tactics.asmdef` | `Tactics` | All runtime game code |
| `Assets/Tests/EditMode/Tactics.Tests.EditMode.asmdef` | `Tactics.Tests.EditMode` | NUnit edit-mode tests |
| `Assets/Editor/Tactics.Editor.asmdef` | `Tactics.Editor` | Editor-only utilities |

## Running Tests

Tests run through Unity's Test Runner (Window → General → Test Runner). The edit-mode tests in `Assets/Tests/EditMode/` use NUnit and do not require entering Play Mode — they test pure-logic classes like `VisionEvaluator` directly.

There are no CLI build or lint commands; all compilation happens inside the Unity Editor.

## Architecture

### Game Loop (`GameManager`)
`Assets/Scripts/Core/GameManager.cs` is a singleton that drives the match lifecycle via a coroutine: **BuyPhase → RoundActive → RoundEnd**, then loops. It fires `OnStateChanged` and `OnTimerUpdated` events that other systems subscribe to. `EconomyManager` is informed at round end.

### Player
- `PlayerController` (`Tactics.Player`) — movement (run/walk/crouch via `CharacterController`), mouse-aim rotation, and centering-camera logic. Exposes `VisionOrigin`, `LookTarget`, and `AimGroundPoint` for downstream systems.
- `TopDownCamera` (`Tactics.Camera`) — orthographic-style top-down camera locked at 90° X rotation. Follows player + mouse midpoint. `QuickAlign` coroutine snaps to a given Y-rotation.

### Vision System
The most complex subsystem. Two parallel layers cooperate:

**CPU layer (entity visibility)**
- `VisionEvaluator` — stateless static methods: cone tests, LOS raycasts, capsule sample-point collection. No Unity scene state; fully testable.
- `VisionConfig` — plain value struct passed to all evaluator calls.
- `EntityVisibilityDriver` — iterates every registered `VisibleEntity` each `LateUpdate` and calls `VisionController.IsEnemyVisibleAt`; toggles their renderers.
- `VisibleEntity` — self-registers in a static list; holds `FeetPosition` and optional capsule overrides.

**GPU layer (fog of war)**
- `VisionController` — owns a hidden perspective "eye camera" placed at the player's head. Each frame it renders depth into `_VisionEyeDepth` (R32F). Sets all `VisionShaderGlobals` for shader consumption. Temporarily disables the player's own renderers during the eye-camera pass to avoid self-occlusion.
- `VisionFogRendererFeature` (URP `ScriptableRendererFeature`) — enqueues `VisionEyeDepthCapturePass` on the eye camera and `VisionFogCompositePass` on all other game cameras.
- `VisionEyeDepthCapturePass` — copies the eye camera's depth buffer into the persistent R32F texture.
- `VisionFogCompositePass` — fullscreen blit pass.
- `VisionFogComposite.shader` — reconstructs world-space positions from the scene depth buffer and for each pixel tests four sample heights (head/chest/knees/feet) against the eye depth map. Pixels not visible are darkened by `_FogStrength`.

**Layer indices** (`VisionLayerMasks`): Wall=6, Ground=7, Dynamic=9; `WallOnly` is the mask both bullet- and melee-blocking queries use. Props are split into Wall (sides) + Ground (top face) child colliders so players can aim onto prop surfaces.

### Combat (server-authoritative)
- `Health` — `NetworkBehaviour`; server-only mutators (`TakeDamage`, `AddShield`, `Heal`, `ServerRevive`) with shield-first absorption, replicated via `NetworkVariable`s; `OnHealthChanged`/`OnShieldChanged`/`OnDeath` fire on every peer from the replicated values.
- `WeaponController` — owner computes the aim point (world position under the mouse) and sends `ShootServerRpc(aimPoint, weaponId)`; the server re-validates fire cadence, resolves the hit against its own world (wall penetration, see below; proximity damage rings on the XZ plane: head <0.5m, body <0.75m, leg <1m), and applies damage. `weaponId` indexes the `weaponRegistry` array serialized on the Player prefab so the server reads stats from its own `WeaponData` copy. Ammo/inventory are still client-trusted until the buy/economy systems are networked.
- **Wall-bang (penetration)**: two independent axes, matching measured Valorant behaviour. The *surface* decides how far a bullet may travel (`WallSurfaceData.maxTravelMeters`, a plain horizontal thickness in metres — Wood 1.0, Stone 0.7, Concrete 0.6, Metal 0.45, unlabelled 0.8); the *weapon's* `PenetrationLevel` (Low/Medium/High on `WeaponData.wallPenetration`) decides the damage curve played out over that distance. A weapon's level therefore never changes *which* walls it can pierce — an Operator and a Classic get through the same geometry, the Classic just arrives with far less. Damage never reaches zero: every level bottoms out on a floor (30% medium/high, 25% low), which is what reproduces the measured minimums (Vandal 160→48, Sheriff 159→47, Spectre 78→19, Bucky 40→10). The curve is analytic, not banded — `mult = floor + (start − floor)·(1 − u)^k` over `u = clamp01((t − head)/(1 − head − tail))`, with a flat `head` at the start (only High keeps full damage through real wall) and a flat `tail` at the end (Low sits on its floor early); all five parameters per level live in `WallPenetration`. Travel distance follows Valorant's "one solid wall" rule: **first entry → last exit**, so air between two pierced objects counts as wall, but a single wall plus a long gap to a distant target costs only its own thickness. Mixed materials are governed by the most restrictive one. Deliberate divergences from the source testing: the Operator's outlier 0.41 floor is treated as a thin-wall artifact (it floors at 0.30 like every other High weapon), and the rare ~2-in-100 "tail" to ~10% at the extreme tip is not reproduced.
- **Shot origin is eye height, not the feet.** The player transform's origin sits at the feet, so `ShootServerRpc` raises `startPoint` by `PlayerController.EyeHeightFor(crouched)` (1.9 standing / 1.4 crouched — the same two numbers the vision origin uses). Penetration is then measured on a **horizontal** segment at that height: the damage model is XZ-planar throughout (`FindClosestTarget` and the hit rings ignore y), so measuring the wall in that same plane is what lets a surface's budget be read as a plain thickness. Spread is unaffected — `ApplyOffsetToAimPoint` zeroes y. Tracers and blocked-shot decals now start/land at eye height instead of the floor.
- **Alt-fire (ADS)**: weapons with `WeaponData.altFireType == AimDownSight` aim via right click — `adsMode` Hold (Vandal: aim while held) or Toggle (Operator: each press cycles no-zoom → level 1 → ... → no-zoom through `adsZoomLevels`, e.g. [2.5, 5]). Aiming narrows the vision cone by the level's tan-space multiplier (pure logic in `AdsZoomLogic`, smoothed in `VisionController`), slows movement (`adsMoveSpeedMultiplier`, per-weapon), scales fire rate (`adsFireRateMultiplier`), swaps spread to the alt-fire column (`altFirstShotSpread*`/`altMaxSpread*`; for an ADS alt-fire only first/max are taken, growth and movement penalties stay shared with hip-fire), and biases the camera toward the crosshair — `TopDownCamera` scales its look weight from `lookWeight` toward `adsMaxLookWeight` by the tan-space zoom fraction `1 − 1/zoom` (pure math in `CameraFollowMath`), so deeper zoom (Operator level 2) pushes the player model further toward the screen edge. The camera bias never moves the *aim*: `TopDownCamera` keeps a "shadow" position (where the camera would be with no bias — bit-exact copy of the real camera while not aiming, independent sim only while the weight is diverged) and each frame warps the OS cursor so the world point under it moves only by the shadow's motion (`CompensatedAimPoint`, per-frame delta re-derived from absolute positions — never a standing offset, which runs away). Warping is skipped while a menu owns the cursor, unfocused, during `QuickAlign` (CenterCamera does its own warp), and clamps to screen bounds; `CrosshairController` runs at execution order 160 (camera 150) and prefers `WarpedCursorScreenPosThisFrame` because `Mouse.current` only reflects a warp at the next input update. ADS state flows like crouch: `PlayerController.IsAiming` (= zoom level > 0) → `PlayerInputTick.Ads` → `PlayerStateSnapshot.IsAds` → server reads `AuthoritativeIsAds`. Toggle zoom resets on weapon switch and reload start. Spread movement penalties are classified from the player's *chosen inputs* (Walk/Crouch flags in the snapshot), never from measured speed — speed modifiers like ADS must not shift the spread band.
- **Shotguns (pellets + damage falloff)**: `WeaponData.pelletCount` > 1 (Judge: 12) fires that many pellets per trigger pull from one `ShootServerRpc` — each pellet rolls its own disc offset from consecutive shot numbers (`serverShotNumber` advances by pelletCount per pull; spray index and recoil once per pull; pure logic in `SpreadCalculator.ComputePelletOffsetsDegrees`). Per-pellet base damage comes from `WeaponData.damageRanges` (distance bands with explicit head/body/leg values since ratios differ per band; looked up by XZ shooter→target distance in `DamageFalloff.GetZoneDamage`; past the last band it keeps applying; empty array = legacy `headDamage × hit-level multipliers`). Pellet damage is summed per target as floats and truncated once — a single `TakeDamage`/`HitConfirmOwnerRpc` per target reporting the best zone hit. All impact FX for a pull ride one batched `ShotImpactsClientRpc` (`PelletImpact[]`); multi-pellet decals fade after `HitFxSpawner.PelletDecalLifetime` (4 s) instead of the prefab's 10 s. `WeaponData.spreadDistanceExponent` controls how the pattern's world radius grows with aim distance (`tan(spread°) · 10^(1-exp) · d^exp`, degrees calibrated at 10 m): 1 = true angular cone (default, all rifles + what recoil assumes), Judge = 0.5 (√d) because against the fixed XZ hit rings a pure cone's hit count decays ~1/d² while measured Valorant damage decays ~1/d (tall first-person silhouette) — √d growth reproduces the measured curve (≈122 avg at 10 m, ≈25 at 20 m, ≈10 at 50 m with 8° base spread).
- **Alt-fire (shotgun burst)**: `WeaponData.altFireType == Shotgun` (Classic) makes right click a discrete 3-pellet burst rather than a stance — one burst per press (`WasPressedThisFrame`, unlike primary fire and the Judge, which repeat while held), `altPelletCount` rounds per pull at the absolute `altFireRate` (2.22/s). It owns the whole alt column: `altFirstShotSpread*`/`altMaxSpread*`, `altSpreadPerShotDegrees`, `altMovePenalty*` and `altSpreadDistanceExponent` (Classic 0.5 while its primary stays a true cone at 1). A burst off a near-empty magazine fires the rounds it has, one pellet each. Because a burst is an action and not a stance, it can't ride the tick-quantized `PlayerStateSnapshot` the way ADS does: `ShootServerRpc(aimPoint, weaponId, altShot, pelletCount)` carries the mode on the shot itself, and the server derives spread column, growth, penalties, exponent and cadence from `altShot` out of its own registry copy (`FireModeStats`), clamping `pelletCount` to the weapon's own max — so a lie can only pick a mode or reduce pellets, never mix the good halves of both. **Both fire modes share one fire timer**, gated on `max(previous shot's interval, this shot's interval)` (`FireModeStats.RequiredGapSeconds`), so a slow burst locks the gun for its full 0.45 s and interleaving can't beat the better single mode; per-mode timers would run both cadences at once. Client and server must compute this identically or the server silently swallows shots, which is why the arithmetic lives in one pure static. One consequence of the tuning is deliberate: the alt cadence far exceeds the spray-decay grace, so pure right-click play always sits at first-shot spread and `altMaxSpread*` only bites someone who was just spraying primary — `sprayDecayDelay` is the knob that changes that.
- **Per-weapon movement speed**: `PlayerInputTick.WeaponId` carries the held weapon's registry index each tick; `Simulate()` resolves it against the server's own `weaponRegistry` copy for `runSpeedPercent` (Operator 0.95 → 5.13 m/s) and `adsMoveSpeedMultiplier` — clients pick which weapon applies but never its values.
- **Equip delay**: `WeaponInventory.IsEquipping` blocks firing, reload-start, and toggle-zoom cycling for `equipSpeed` seconds after the active weapon changes (switch, buy-into-hands, spike fallback; client-trusted like ammo).
- **Melee (Knife)**: `WeaponType.Melee` is the discriminator (not `AltFireType`, since both of its modes are swings) — `FireModeStats.IsMelee`/`IsMeleeAlt`. A swing leaves the bullet path entirely: no aim point, spread, pellets, falloff, or wall-penetration budget. The owner sends `MeleeSwingServerRpc(weaponId, altShot)` — no aim point, because the server already owns the attacker's authoritative position *and* facing — and the server rejects it unless its own registry copy agrees the weapon is melee. `ResolveMeleeServer` sweeps `HitboxHistory.All` for the nearest target inside a box straight ahead (`MeleeCombat.TryGetForwardDistance`: forward component within `meleeRange` 2 m, lateral within `HitZoneRadii.Leg` — a box, not a capsule, so reach never exceeds the stated range), rejects any target with a Wall between (a knife has no thickness budget), and picks damage by which hemisphere the attacker stands in relative to the target's facing (`MeleeCombat.IsBackHit`, rear hemisphere = behind the shoulder plane): Knife 50 front / 100 back primary, 75/150 alt, all four serialized on `WeaponData`. Primary repeats while held (1.6/s); alt is one swing per press at the absolute `altFireRate` (1.1/s) and shares the same `RequiredGapSeconds` timer as every other weapon, so knife↔gun interleaving can't beat either cadence. A swing zeroes `serverSprayIndex` like a weapon switch, raises no `EmitShootSound` (it isn't a gunshot), and spawns no FX — the only FX vocabulary is a bullet tracer plus decal, and a tracer over a 2 m swing reads wrong. The airborne ×0.5 penalty is a spread-era jump-peek rule and deliberately does not apply.
- **Lag compensation**: `HitboxHistory` (on Player and TargetDummy prefabs) records each entity's authoritative position **and yaw** per network tick, server-side only, in a static `All` registry. Yaw is what makes lag-compensated backstabs correct: `UpdateRemoteView` drives a remote player's `transform.rotation` from the interpolation-delayed view buffer *even on the server*, so front/back must be judged from `GetYRotationAt` (fed by the new `PlayerMovementNetwork.AuthoritativeYRotation`), never `transform.forward`. `WeaponController.ShootServerRpc` rewinds hit resolution by the shooter's transport RTT + remote-view interpolation delay (server-measured — clients never send timestamps), capped at 1 s. The damage model is positional (XZ rings), so no physics-scene rewind is needed. Histories are wiped on `ServerTeleport` so rewound shots can't hit vacated respawn corpses.
- Player death → `PlayerMovementNetwork.ServerHandleDeath` teleports to spawn and revives one frame later (so spike drop sees the corpse position). Target dummies use `AutoRevive` instead.

### Netcode
- `PlayerMovementNetwork` — server-authoritative movement with owner prediction/reconciliation, remote-view snapshot interpolation (`interpolationDelayTicks` behind newest), and `ServerTeleport` (bumps `TeleportCount` in the snapshot so owners clear prediction and views cut instead of gliding). **All movement must go through `Simulate()`** or reconciliation reverts it; `ServerTeleport` is the one sanctioned exception.
- `NetworkSpawnMarker` — scene marker that server-spawns a registered network prefab at its own transform on session start (used for the spike pickup and target dummies; in-scene-placed NetworkObjects are avoided because despawn-destroying them is discouraged by NGO).
- Spike carry state exists twice: the owner's local `HasSpike` (HUD/plant checks) and the server instance's `HasSpike` (authoritative — granted in `SpikePickup.TryGrant`, cleared via `ServerClearSpike` on plant/death).

### Economy (`EconomyManager`)
Valorant-style cred system: round-win (3000), loss-streak bonuses (1900/2400/2900), kill reward (200), plant reward (300). Halftime resets to 800. Fires `OnCredsChanged`.

### Objectives
- `Spike` / `SpikeSite` / `SpikeController` — plant (4 s hold) and defuse (7 s hold) interactions gated on `GameState.RoundActive` and trigger-volume proximity.
- **Plant site geometry is two separate meshes per site**, not one: a flat visual/walkable mesh (cut out of Ground, `PlantArea.mat`, non-convex non-trigger `MeshCollider` for standing on) plus a child object holding a separately modeled *solid* trigger mesh (`SpikeSite`'s `MeshCollider`, Convex + Is Trigger, no renderer). The trigger mesh is a Blender duplicate of the footprint with a Solidify modifier (2 m thickness, raised 1 m) so it has real vertical volume spanning the player's 2 m `CharacterController` height. A convex-hull trigger built directly from the flat footprint mesh doesn't work — a zero-thickness mesh's convex hull is itself degenerate, so a `CharacterController` resting on top of it never truly overlaps it and `OnTriggerEnter` won't fire reliably.

### Sound
`SoundEmitter` tracks last move/shoot emit timestamps and exposes `IsCurrentlySounding` for the `SoundVisualizer` to draw radius circles. No audio clips — it's a pure gameplay-signal system.

### UI (UI Toolkit)
All screen UI is UI Toolkit, no uGUI: scene objects `HUD` (`HUDController` — ammo + weapon slots) and `BuyMenuUI` (`BuyMenuController`) each hold a `UIDocument` sharing `Assets/Scripts/UI/PanelSettings.asset` (ScreenSpaceOverlay, ScaleWithScreenSize 1200×800). UI controllers find the local player lazily each `Update` via `NetworkManager.Singleton.LocalClient.PlayerObject` (the player spawns after the HUD), and must call their refresh once right after subscribing to inventory events (the default equip fires before subscribers exist).

**Crosshair** — `CrosshairController` (on the HUD object) hides the OS cursor and draws a Painter2D crosshair at the mouse: a "+" normally, and, whenever the *current* trigger pull would throw more than one pellet (a shotgun always, the Classic while right click is held — `WeaponController.CurrentPelletCount`), a circle showing the true pellet footprint at the aim point — `SpreadCalculator.ComputeSpreadWorldRadiusMeters(xzDistance, spreadDeg)` (the same `d·tan θ` projection pellets use) projected to panel pixels via two `CameraTransformWorldToPanel` points. Its inputs are owner-local and zero-latency: `WeaponController.CurrentSpreadDegrees` (an owner-side spray-index mirror advanced/decayed/reset with the same pure `SpreadCalculator` calls and on the same events as `serverSprayIndex` — cosmetic only, the server never reads it), `WeaponController.TryGetAimPoint` (the same raycast `Shoot()` sends, so crosshair and shot can't disagree), and `PlayerMovementNetwork.PredictedGrounded`/`PredictedHorizontalSpeed` (owner prediction state, not the RTT-lagged snapshot). `CrosshairSettings` (serialized on the controller) is the future customization surface (color, gap, thickness…). `CrosshairController.MenuOpen` — set by `BuyMenuController` — hands the OS cursor back while a menu is open.

## Key Conventions

- Singletons use `Instance` with `Awake` guard (`if (Instance == null) Instance = this; else Destroy(gameObject)`).
- `VisionController.Active` is a static reference to the currently-active controller; the renderer feature accesses it this way.
- Shader property IDs are cached in `VisionShaderGlobals` to avoid per-frame string lookups.
- `[DefaultExecutionOrder(100)]` on `VisionController` and `[DefaultExecutionOrder(101)]` on `EntityVisibilityDriver` ensure vision data is ready before entity visibility is evaluated.
- The eye camera is created at runtime (`HideFlags.DontSave`) and parented to the player; it must not appear in saved scenes.

### Map import (Blender → Unity)
The map is authored in Blender and re-exported whole; `Assets/Editor/MapImportPostprocessor.cs` (an `AssetPostprocessor`) does the entire fix-up on re-import, so dropping in the FBX is the whole workflow. Everything is driven by the Blender **object name**, because Blender materials are replaced by Unity ones as part of that same pass and so cannot carry the signal:

| Blender name | Result |
|---|---|
| `Wall_*`, `Prop_*` | Wall layer, `Walls.mat`, non-convex `MeshCollider`, `WallSurface` component |
| `Ground_*SitePlantArea` | Ground layer, `PlantArea.mat`, non-convex `MeshCollider` |
| `Ground_*` | Ground layer, `Ground.mat`, non-convex `MeshCollider` |
| `Trigger_*` | Convex + IsTrigger `MeshCollider`, `MeshRenderer` stripped, `SpikeSite` added with `siteName` from the last name token |

A prop's walkable top face is a separate piece named `Ground_*`, not `Prop_*`, which is what keeps the Wall-sides / Ground-top split the vision and aiming systems rely on. The penetration surface comes from **any** underscore-separated token matching a `WallSurfaceData` asset name, case-insensitively (`Wall_Stone_01`, `Prop_Crate_Wood_03`), so token order is free and an unmatched name just falls back to the default budget. The pass is self-gating — a model with none of these prefixes (e.g. `Spike.fbx`) is left completely alone, so no path allowlist is needed.
